# Несоответствия и проблемы бэкенда

Формат строки: **[область] файл:строка — суть — воздействие на UI — обходной путь.**
Агент B (настройка и данные) дописывает свой раздел; другие агенты — свои.

## B — Настройка и данные

### Конструктор воронок

1. **Нет ручки чтения задачи сопоставления.** `workflow/schemas.py:242` объявляет `StatusMappingJobOut`, но в `workflow/router.py` нет `GET /workflows/{id}/mapping-jobs/{job_id}` (и списка). После `POST …/archive` при > 100 сделок задача остаётся `running`, а UI не может показать прогресс (`processed_count / affected_count`) и итог (`failed_count`, `report`). Обход: после архивации опрашиваем `GET /workflows/{id}` раз в 2 с и ждём `statuses[].is_archived = true` у архивируемого статуса; прогресс — «неопределённый» (`Progress indeterminate`) с текстом «Переносим N сделок…». Просьба: добавить `GET /workflows/{id}/mapping-jobs/{job_id}`.
2. **Ошибки валидации — плоские строки.** `workflow/schemas.py:198` `ValidationIssue{code,message,path}` не используется; `ValidateResponse.errors: list[str]` (`service.py:697-780`). Чтобы подсветить проблемные узлы/рёбра на холсте, UI парсит текст регулярками (`transitions[<имя>]…`, «Недостижимые из initial статусы: a, b», «…(ловушки): a, b»). Хрупко: смена формулировки сломает подсветку. Обход: клиентский валидатор-зеркало (`features/config/workflows/validation.ts`) считает всё «на лету» сам, серверный ответ — только подтверждение. Просьба: возвращать `issues: [{code, message, path}]`.
3. **`POST /workflows/{id}/validate` пишет запись аудита на каждый вызов** (`service.py:410`). Валидацию «на лету» при каждом изменении графа на сервер отправлять нельзя (спам аудита). UI валидирует локально, сервер зовёт только по кнопке «Проверить» и перед публикацией.
4. **Нельзя архивировать/удалить/переименовать воронку.** Состояние `archived` есть в модели (`models.py:42`, фильтр `state`), но ручки нет; нет `PATCH /workflows/{id}` (name, is_default) и `DELETE` черновика. UI: в списке нет действий «Архивировать»/«Удалить»/«Переименовать», `is_default` меняется только при создании. Просьба: `PATCH /workflows/{id}` + `POST /workflows/{id}/archive`.
5. **Удаление статуса со сделками через `PUT /graph` даёт 500.** `service.py:303-308` удаляет статусы, не попавшие в тело; `crm/models.py:154` — `deals.status_id … ondelete="RESTRICT"`; в `core/problem.py` `IntegrityError` не маппится в Problem Details → пользователь увидит «Внутренняя ошибка». Обход: при удалении узла с холста UI сначала зовёт `GET …/statuses/{id}/impact`; если `active_count > 0` — блокирует удаление и открывает мастер архивации (как и требует §4.11). Просьба: возвращать 409 с кодом вместо 500.
6. **`impact.problem_deals` всегда пуст** (`crm/service.py:500-507`): список сделок без обязательных полей целевого статуса (§4.11 п.4) не считается, потому что цель на шаге impact не известна. Ручка не принимает `target_status_id`. UI показывает `required_fields` целевого статуса и предупреждение «сделки без этих полей уйдут в резервный статус», точного списка нет. Просьба: `GET …/impact?target_status_id=` с расчётом `problem_deals`.
7. **`StatusArchiveRequest.mapping_rules` — свободный `dict`**, сервис их не интерпретирует (`service.py:548` просто сохраняет). Правила «по типу сделки / по сумме» (§4.11 п.3) не реализованы. UI: один целевой статус + резервный, без правил.
8. **`GET /workflows/{id}` отдаёт SLA только для живых правил**, а `sla_rules` в `PUT /graph` полностью перезаписываются: `escalate_to_user_id` — просто UUID без имени. UI подставляет имена через `/api/admin/users`? (чужая область). Пока: поле «Эскалация на пользователя» показываем как поиск по пользователям только если лид даст общий `UserPicker`; иначе — только роль.

### Справочники

9. **Нет `DELETE` ни у одного справочника**; у `directions` и `holidays` нет и `is_active`. Ошибочно созданную запись нельзя убрать. UI: «Удалить» отсутствует, у продуктов/причин/полей — переключатель «Активно».
10. **Циклы в иерархии направлений не проверяются** (`catalog/service.py:860-884` принимает любой `parent_id`, в т.ч. потомка). UI исключает из выбора родителя сам элемент и его потомков.
11. **`valid_from > valid_to` у продукта не проверяется** (`service.py:927-958`). UI валидирует сам.
12. **`GET /directions` постраничный (limit ≤ 100)**, а UI нужно дерево целиком → грузим все страницы подряд. Просьба: `?all=true` или `limit` без ограничения для маленьких справочников.

### Импорт

13. **Нет ручки построчных результатов** (`import_row_results`): в `imports/router.py` только счётчики `ok/warn/error` и файл ошибок `result_file_id`. Строки с ошибками нельзя показать в интерфейсе — только скачать .xlsx. Просьба: `GET /imports/{id}/rows?status=error&cursor=`.
14. **`ImportJobOut` не содержит причины сбоя** (`schemas.py:23-43` нет `error`), статус `failed` при этом объявлен. Обход: показываем «Не удалось», без деталей.
15. **Пресет применяется молча**: `service.py:170-174` накладывает последний сохранённый пресет на автоподбор без указания, какой именно. `ImportProfileResponse` не сообщает, что применён пресет. UI отдельно грузит `GET /import-presets?entity_type=` и даёт выбрать явно; нет `DELETE /import-presets/{id}`.
16. **Отчёт об ошибках доступен только через `GET /files/{id}/download-url`** (модуль files) — нужен `file:download` (есть у HEAD/ADMIN, ок).

### Отчёты и дашборды

17. **Коды CRM-1601/1602/1603 не используются.** `core/errors.py:63-65` объявлены, но `reporting/service.py:284,287` бросают `CRM-1001` (422) и для «ещё не готов», и для «истёк срок хранения»; лимита параллельных отчётов на создание нет вообще (`reports_max_concurrent` только ограничивает воркер). UI различает случаи по `status`/`expires_at` (`expires_at < now` → «срок хранения истёк»), а не по коду; готово обрабатывать и 429/410, если появятся.
18. **`ReportJobOut` без `file_id` и `params`** (`schemas.py:51-64`): нельзя ни понять, что файл удалён ретеншеном (кроме `expires_at`), ни «повторить с теми же параметрами». `progress_pct` никогда не обновляется (`service.py:196-252`) → всегда 0. UI: неопределённый индикатор, повтор — по шаблону с параметрами по умолчанию.
19. **Данные для дашборда получить нельзя.** `reporting/models.py:29-33`: виджеты ссылаются на отчёт (`config.template_code/params`), а содержимое предлагается брать через `POST /reports` — но он отдаёт файл (xlsx/pdf/png), а не JSON, и каждый вызов создаёт файл в S3 + событие аудита `REPORT_EXPORTED`. График из xlsx в браузере без зависимостей не построить. Обход на Фазу 2: `report_chart` = PNG-картинка (только `deal_funnel`/`monthly_dynamics`, у которых есть `png`), `report_table` = ссылка на скачивание + число строк, `stat_tile` = `row_count` отчёта. **Просьба (приоритетная): `format: "json"` или `GET /reports/{id}/data` → `{columns, rows}`** — тогда виджеты рисуются `@lct-testkit/rt-ui/charts`.
20. **Роутер `GET /reports` не пробрасывает фильтр `template_code`**, хотя сервис его поддерживает (`service.py:138`). Мелочь.

### Реестр ЕГРЮЛ

21. **Импорт поддерживает только `source=fns_egrul`** (`registry/tasks.py:88`), остальные значения → `failed`. UI предлагает только ФНС; `rosobrnadzor`/`manual` показываем как недоступные.
22. **Нет прогресса импорта**: `entries_count` пишется только по завершении, нет `GET /admin/registry/versions/{id}`. UI опрашивает список каждые 3 с, пока есть `pending/running`.

### Интеграции

23. **Нет повторной отправки dead-letter** (`integration/router.py`): события `failed/dead` только читаются, ручки `retry` нет. Кнопка «Повторить» невозможна. Просьба: `POST /admin/integrations/outbox-events/{id}/retry`.
24. **Списки без курсорной пагинации** (`limit ≤ 200`, без `cursor`, без фильтра по дате). UI: «последние N», без «Показать ещё».
25. **`/health/ready` отвечает 503 при падении критичной зависимости** (`api/health.py:72`) с тем же JSON. Общий `unwrap` бросит ошибку — индикатор здоровья читает ответ «сырым» `fetch` и разбирает JSON при любом статусе.
26. Публичные `POST /api/v1/integrations/*` — HMAC-подпись секретом из переменной окружения (`credentials_ref`), секрет браузеру недоступен по замыслу (`integration/models.py:14-17`). «Тестовая отправка» из UI невозможна без раскрытия секрета — не делаем, см. plan-config.md.

### Шаблоны уведомлений

27. **Нет предпросмотра рендера и списка переменных** для Jinja2-шаблонов (`notification/router.py`). UI подсказывает переменные по известным кодам событий из `notification/seed.py`; проверить синтаксис до сохранения нельзя. Просьба: `POST /admin/notification-templates/preview {body_template, payload}`.
28. Нет `DELETE` шаблона; деактивация через `is_active`.

### Найдено при проверке на живом бэкенде (Фаза 2)

29. **`deploy/entrypoint.sh seed` засевает только воронки** (`app.modules.workflow.seed`); сиды `reporting`, `notification`, `integration` (`python -m app.modules.<модуль>.seed`) в контейнер не входят → в свежей БД нет шаблонов отчётов (галерея «Отчёты» пуста), шаблонов уведомлений и источников интеграций. Обход: запущены вручную командой `docker exec rtk-crm-api-1 python -m app.modules.{reporting,notification,integration}.seed`. Просьба: добавить в `seed`.
30. **JIT-пользователь откатывается вместе с транзакцией, а Redis-кэш принципала остаётся** (`core/deps.py:143-153` — `set_principal_cache` до commit; `core/db.py` откатывает всё при исключении). Если первым запросом нового пользователя был не `GET /api/me` (например, `/api/workflows` без принятого согласия → 403 CRM-1105), строка `users` пропадает, а кэш (`cache:kcid:*`, `cache:perm:*`) указывает на неё → `/api/me` даёт 500 `NoResultFound` (`router_me.py:95`) до сброса кэша. Обход: удалить два ключа в Redis; сид/тесты всегда начинают с `GET /api/me`.
31. **Нет признака «есть неопубликованные правки»** у воронки: `WorkflowOut` не говорит, отличается ли черновик от опубликованного снимка. UI считает по `updated_at > published_at + 2 с` (после любого `PUT /graph` даже без изменений показывается «Не опубликовано»). Просьба: `has_unpublished_changes` (сравнение хэша черновика со `graph_hash`).
32. **Пользовательские поля не проверяются на сервере**: `custom_field_defs.options/validation` хранятся как есть, значения `custom_fields` не сверяются с определениями (обязательность, тип, границы). UI-договорённость (для форм A): `options = {"choices": [...]}`, `validation = {"min","max"}` / `{"max_length","pattern"}`.
33. **Дубль кода в справочниках отвечает 422, а не 409** (`POST /directions` с существующим `code`) — под поле «Код» попадает только благодаря разбору текста; желательно `CRM-1301` / 409 с `errors[{field:'code'}]`.
34. **Тестовые данные не убрать**: нет `DELETE` у направлений, праздников, шаблонов уведомлений, версий реестра, воронок (см. #4, #9, #28) — демо-стенд копит записи, созданные при проверке.

## A — CRM (сделки, организации, контакты, задачи, файлы, уведомления)

### Пользователи и права

1. **[identity] `identity/router_admin.py:68,76-88`, `core/permissions.py:97-132` — единственный список пользователей `GET /admin/users` (и `/admin/teams`) требует `user:read`, которого нет у KAM и HEAD.** При этом `ParticipantOut` (`crm/schemas.py:243-251`), `CommentOut.author_id` (`:281`), `TaskOut.assignee_id`, `DealOut.owner_id`, `DealStatusHistoryOut.changed_by` отдают только UUID. Воздействие: у HEAD/KAM нельзя показать имена авторов/ответственных/исполнителей и нельзя выбрать преемника при `POST /deals/{id}/reassign` (право `deal:reassign` у HEAD есть, а список кандидатов — нет), участника, исполнителя задачи, упоминание. Обход: имена берём из `/api/me` (себя) и `/admin/users` (ADMIN), остальные — «Сотрудник ·a1b2» по короткому id; пикеры у HEAD/KAM ограничены известными id (ответственный, участники). **Просьба (приоритетная): открыть `GET /admin/users` для HEAD (скоуп команды) и KAM с усечёнными полями, либо `GET /users/directory?ids=&q=`.**
2. **[crm] `crm/service.py:1073` — `DealCreateRequest.owner_id` принимает любого пользователя без проверки скоупа/существования в команде.** KAM может создать сделку «на коллегу». UI: поле «Ответственный» показываем только HEAD/ADMIN.

### Переходы и воронка

3. **[crm] `crm/service.py:705-740` (`"attachments": {}`), `crm/schemas.py:175-177` — guard по вложениям невыполним.** Контекст DSL всегда отдаёт пустые `attachments`, поле `attachments` в `TransitionRequest` не обрабатывается (модуль files давно есть). В сидах `workflow/seed.py:226-231` (`contract_signing → lms_transfer`: подпись ИЛИ вложение) и `:298-303` (`payment_contract → lms_enrollment`: вложение ИЛИ `custom_fields.payment_confirmed`) ветка «вложение» мёртвая. UI: подсказка «Прикрепите договор» показывается, но переход проходит только по альтернативе (подпись / флаг оплаты); в чек-листе условие помечено «не проверяется сервером». Просьба: строить `attachments.{category}` из `attachments` по `entity_type='deal'`.
4. **[crm] `crm/service.py:1217-1227` — `available-transitions` отдаёт плоский список листьев условий**, структура `any/all` теряется: для `any` из двух условий оба будут `satisfied=false`, и по ответу нельзя понять, что достаточно одного. Обход: дерево `transitions[].conditions` читаем из `GET /workflows/{id}` (кэш по `workflow_id`) и сопоставляем по `transition.id`. Просьба: вернуть `conditions_tree` (или `groups`).
5. **[crm] `crm/service.py:1262-1318`, `workflow/schemas.py:79` — `required_fields` целевого статуса при переходе не проверяются** (только `conditions`). Сид компенсирует условиями для won/lost, но статус, созданный в конструкторе только с `required_fields`, пропустит сделку без полей. UI использует `required_fields` для формы, блокировать не может.
6. **[crm] `crm/router.py:252-265`, `crm/service.py:797-819` — карточка кэшируется по `version`, а комментарии (`service.py:1761-1792`) и задачи (`:1873-1901`) версию не меняют** → `comments_count`/`open_tasks_count` устаревают до 10 мин (TTL). UI считает счётчики по данным вкладок, карточку — только для полей сделки.
7. **[crm] `crm/schemas.py:81-95` — `DealUpdateRequest` без `products`**: продукты сделки задаются только при создании, изменить/добавить/удалить нельзя (нет и отдельной ручки). UI: продукты — только чтение в карточке, выбор — в форме создания. Просьба: `PUT /deals/{id}/products` или `products` в PATCH.
8. **[crm] `crm/service.py:1161-1167` — `custom_fields` в PATCH сливаются с существующими**, удалить ключ нельзя (только записать `null`). UI шлёт `null` для очистки.
9. **[crm] `crm/tasks.py:35-37` vs `workflow/schemas.py:136` — порог предупреждения SLA зашит (0.75), `warn_threshold_pct` правила не читается.** UI считает состояние на клиенте с тем же 0.75.
10. **[workflow] `workflow/seed.py:395` — сид-воронки публикуются без `sla_rules`** → `sla_due_at = null` у всех демо-сделок; фильтры «SLA» и индикаторы в демо пусты, пока правила не добавлены через конструктор (область B). Просьба: сид с SLA (например, 3 рабочих дня на промежуточный статус).

### Список сделок

11. **[crm] `crm/router.py:111-158`, `crm/service.py:913-968` — нет `total`, нет параметра сортировки, один `status_id` (нет мультивыбора), нет фильтра «открытые/закрытые» или по типу статуса.** Воздействие: счётчики вкладок невозможны; сортировка по колонкам — только в пределах загруженных строк; «Закрытые» — через `closed_from=1970-01-01`, «открытые» отфильтровать нельзя; доска-канбан группируется на клиенте по страницам `workflow_id=`. Просьба: `status_id` списком, `is_closed`, `sort`.
12. **[crm] `crm/router.py:472-481`, `:379-393` — комментарии и история без пагинации** (все записи разом). Для длинных обсуждений будет тяжело; UI отрисовывает всё, треды сворачивает.
13. **[crm] `crm/schemas.py:318-334` — `TaskOut` без номера/названия сделки**, а у `/deals` нет фильтра `ids=` → на странице задач N+1 запросов карточек. Обход: пакетная подгрузка с кэшем и ограничением параллельности. Просьба: `deal_number`/`deal_title` в `TaskOut` или `GET /deals?ids=`.
14. **[crm] `crm/schemas.py:261-266`, `crm/models.py:356` — у комментария есть `body_format`, но задать его при создании нельзя (всегда `plain`)**, хотя new_spec §7.5 описывает markdown. UI рендерит Markdown безопасно (`marked` + `DOMPurify`, без raw HTML) независимо от поля.
15. **[crm] `crm/router.py:161-199` — `Idempotency-Key` только у `POST /deals` (и `POST /organizations`, `POST /contacts`)**; комментарии, задачи, участники, вложения без защиты от повтора. UI блокирует кнопку на время запроса.
16. **[crm] Нет ручки удаления сделки** (матрица прав new_spec ч. 5 отдаёт ADMIN «soft delete»); UI без «Удалить».
17. **[crm] `crm/schemas.py:111,197` — `amount`/`price`/`total` (Decimal) и `duration_in_prev` (timedelta) сериализуются строками** (`"1250000.00"`, `"P1DT2H30M"`). Не баг, но клиенту нужен парсинг (`shared/duration.ts`).

### Организации, контакты, реестр

18. **[catalog] `catalog/router.py:185-220`, `catalog/service.py:286-293` — при дубле по ИНН `extra.deleted=true`, но ручки восстановления нет; «Запросить доступ» из dop.md §11.6 — тоже нет.** UI показывает текст «удалена/недоступна — обратитесь к администратору/руководителю».
