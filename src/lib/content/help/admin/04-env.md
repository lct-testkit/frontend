# Переменные .env и секреты

Вся настройка стенда лежит в файле `.env` и в двух сгенерированных рядом с ним конфигах. Глава объясняет, что создаёт установщик, какие значения можно менять, а какие нельзя.

## Что понадобится

- Доступ к каталогу окружения: `/srv/rtk-<окружение>` при установке через `scripts/deploy.sh` или каталог `compose/` рядом с `install.sh` у офлайн-пакета.
- Привычка не печатать значения секретов в чат, тикеты и скриншоты. В примерах этой главы только имена переменных.

## Что создаёт установщик

Команда `--init` (скрипт `scripts/gen_env.sh`) создаёт три файла и подставляет в них одни и те же случайные секреты:

| Файл | Что в нём |
| --- | --- |
| `.env` | Все переменные окружения; права `600` (читает только владелец) |
| `runtime/keycloak/realm-crm.json` | Настройки входа (realm) с теми же секретами клиентов |
| `runtime/seaweedfs/s3.json` | Ключи доступа к файловому хранилищу, совпадающие с `.env` |

Секреты согласованы между файлами. Правка секрета только в `.env` приводит к рассинхрону: приложение и Keycloak или хранилище перестают понимать друг друга. Вход перестаёт работать.

## Какие значения где

| Переменные | Для чего | Менять ли |
| --- | --- | --- |
| `POSTGRES_PASSWORD`, `CRM_APP_PASSWORD` | Пароли базы данных: владельца и ограниченной роли приложения | Нет: пароль записан в томе базы при создании |
| `KEYCLOAK_ADMIN_PASSWORD` | Пароль администратора консоли Keycloak (логин `admin`) | Нет: читается только при первом запуске, см. главу «Keycloak и пользователи» |
| `KEYCLOAK_CLIENT_SECRET`, `KEYCLOAK_ADMIN_CLIENT_SECRET` | Секреты клиентов `crm-bff` и `crm-admin` в Keycloak | Нет: они же прописаны в realm |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | Ключи файлового хранилища | Нет: они же прописаны в `s3.json` |
| `SIGNATURE_SERVER_SECRET` | Защита целостности подписи | Нет: это ключ метки целостности подписи |
| `AUDIT_HMAC_KEY` | Ключ цепочки журнала аудита | Нет, но хранить копию (см. ниже) |
| `SETTINGS_ENCRYPTION_KEY` | Ключ шифрования секретных системных настроек | Нет, но хранить копию (см. ниже) |
| `CMS_WEBHOOK_SECRET`, `GRAFANA_ADMIN_PASSWORD` | Подпись входящих запросов с сайта; пароль Grafana | По необходимости, согласованно с другой стороной |
| `BASE_URL`, `CRM_TLS_HOST`, `TLS_MODE` и производные от них | Адрес и режим TLS | Только скриптом `scripts/set_host.sh` (глава «TLS и домен») |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_STARTTLS` | Почтовый сервер | Да (глава «Почта и SMTP») |
| `GRAFANA_ANONYMOUS_VIEWER`, `PROMETHEUS_RETENTION` | Мониторинг | Да (глава «Мониторинг и логи») |
| `UVICORN_WORKERS` | Число процессов API на контейнер | Нет, оставьте `1` (глава «Масштабирование») |

## Какие переменные действуют

В контейнеры `api`, `worker`, `migrate` и `seed` попадают только переменные из фиксированного списка в `docker-compose.yml`. Остальные строки файла `.env.example` (лимиты размера файлов и импорта, сроки сессии, настройки приглашений и обезличивания) в файле есть, но в контейнеры не передаются: там действует значение по умолчанию из кода приложения, даже если в `.env` записано другое. Действуют: `APP_PROFILE`, `BASE_URL`, `KEYCLOAK_*`, `ALLOW_BEARER_AUTH`, `S3_*`, `SIGNATURE_SERVER_SECRET`, `LOG_LEVEL`, `LOG_JSON`, `WORKER_METRICS_PORT`, переменные интеграций (`CMS_WEBHOOK_SECRET`, `LMS_BASE_URL`, `BITRIX_*` и их `*_REF`), `INTEGRATION_WEBHOOK_RATE_LIMIT_PER_MIN`, `ALLOWED_FILE_EXTENSIONS`, `AUDIT_HMAC_KEY`, `SETTINGS_ENCRYPTION_KEY`, `SMTP_*`, `SIGNATURE_EXPOSE_DEBUG_OTP` и `UVICORN_WORKERS`.

Значения по умолчанию, которые сейчас действуют в боевом окружении: сессия живёт 12 часов (`SESSION_TTL=43200`), простой до выхода — 30 минут (`SESSION_IDLE_TIMEOUT=1800`), токен доступа — 5 минут (`ACCESS_TOKEN_TTL=300`).

## Шаги: сохранить ключи вместе с бэкапом

Установщик создаёт два случайных ключа:

- `AUDIT_HMAC_KEY` защищает цепочку журнала аудита. Без него цепочку может пересчитать целиком тот, у кого есть доступ к базе. Смена ключа не позволяет проверить записи, подписанные прежним.
- `SETTINGS_ENCRYPTION_KEY` шифрует секретные системные настройки. Потеряв его, вы не сможете прочитать зашифрованные настройки.

Резервная копия базы **не содержит** файл `.env`, а значит и эти ключи. Храните копию `.env` вне сервера вместе с архивами базы (глава «Резервные копии и восстановление»). Если стенд поставлен раньше и ключей не имеет (аудит остаётся на прежнем формате хэша), добавьте значения в `.env` вручную и перезапустите `api` и `worker`.

## Смена секретов

В поставке нет проверенной процедуры ротации секретов и нет скрипта для неё. Что важно знать:

- Секреты связаны между файлами (таблица выше), а пароли базы записаны в томах. Правка одного значения вручную ломает связь.
- Команда `gen_env.sh` при уже существующем `.env` отказывается работать. Флаг `--force` заменяет **все** секреты новыми, включая пароли базы, привязанные к существующим томам: на стенде с данными его использовать нельзя.
- Если секрет скомпрометирован, планируйте переустановку с переносом данных из резервной копии и заранее согласуйте это с владельцем системы.

## Как проверить

Права на файл и отсутствие демонстрационных значений:

```bash
ls -l /srv/rtk-prod/.env
```

У `.env` должны быть права `-rw-------`. Затем сравните `.env` с `compose/.env.example`: значения переменных, помеченных там «СМЕНИТЬ ДЛЯ PROD», не должны совпадать. Скрипт `scripts/deploy.sh` для `RTK_ENV=prod` сам откажется запускаться, если нашёл демонстрационные секреты.

## Если не получилось

- Вход перестал работать после правки `.env` — вы изменили секрет только в одном месте. Верните прежнее значение из резервной копии `.env`.
- Почта не уходит — глава [«Почта и SMTP»](?s=admin-smtp).

Сверено с репозиторием `deploy` (ветка main на 18.10.2026, релиз v0.5.3): `compose/.env.example`, `scripts/gen_env.sh`, `compose/docker-compose.yml`, RUNBOOK. Команды этой главы на чистой машине не прогонялись.
