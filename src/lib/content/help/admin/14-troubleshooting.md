# Неполадки

Таблица «симптом — причина — что делать» для сервера. Если в окне ошибки есть код вида `CRM-1201`, сначала посмотрите главу «Коды ошибок» в разделе «Справочник».

## Что понадобится

- Доступ к серверу и умение читать журналы сервисов (глава «Мониторинг и логи»).
- Два общих приёма. Контейнер в цикле перезапусков: смотрите последние строки журнала (`docker compose … logs <сервис> --tail 100`), а не поток `-f`; `docker compose … ps` покажет состояние `Restarting`. Стенд в целом ведёт себя странно, причина неясна: `docker compose … up -d` безопасна в любой момент, она пересоздаёт только то, что разошлось с текущими `docker-compose.yml` и `.env`.

## Шаги: найти симптом

Найдите строку с вашим симптомом в таблицах ниже: они сгруппированы по этапу.

### Установка и выкладка

| Симптом | Причина и что делать |
| --- | --- |
| `required variable API_IMAGE is missing` | Не передан файл со ссылками на образы: `python3 scripts/render_env_images.py > .env.images` (или запускайте через `scripts/deploy.sh`) |
| `unauthorized` при скачивании образов | Токен истёк или вход в реестр не выполнялся: `docs/ghcr-setup.md`, шаг 1 |
| Таймер автообновления есть, образы не обновляются | `journalctl -u rtk-demo-autodeploy.service`: конфликт `git pull` (не правьте файлы репозитория вручную) или проверка нового образа на стороне разработки не прошла |
| После отката образы старые, а схема базы новее кода | Миграции необратимы: восстановление из копии перед выкладкой (главы «Обновление и откат» и «Резервные копии и восстановление») |
| `up --wait` падает на `seaweedfs` на холодном старте | Смотрите `docker compose … logs seaweedfs`; у проверки есть `start_period: 40s`, на очень медленных дисках его увеличивают |
| Нужно понять, что реально задеплоено | `docker compose … images` и сверка тега и дайджеста с `images.yaml` |

### Вход и адреса

| Симптом | Причина и что делать |
| --- | --- |
| При входе на новом адресе `invalid_redirect_uri` | Адрес менялся без `scripts/set_host.sh`: выполните его (глава «TLS и домен») |
| Вход не работает после смены секретов | Секреты меняли только в `.env`. Верните прежние значения из копии; процедуры ротации в поставке нет (глава «Переменные .env и секреты») |
| Пароль администратора консоли Keycloak из `.env` не подходит | Он читается только при первом старте; порядок восстановления — в главе «Keycloak и пользователи» |
| Приглашённый сотрудник не может задать пароль и войти | Ссылка истекла или уже использована («Ссылка недействительна»): выдайте новую в карточке сотрудника. Почта Keycloak для задания пароля не нужна (главы «Keycloak и пользователи», «Почта и SMTP») |
| Письма (приглашения, ссылки на подписание, уведомления) не приходят | Без `SMTP_HOST` письма приложения остаются в очереди; Keycloak шлёт свою почту отдельно (глава «Почта и SMTP») |
| «Учётная запись не заведена в CRM» | У пользователя Keycloak нет роли CRM: назначьте роль (глава «Keycloak и пользователи») |
| Предупреждение браузера о сертификате | Ожидаемо для самоподписанного сертификата (режимы `internal` и `off`): установите корневой сертификат Caddy (глава «TLS и домен») |

### Работа системы

| Симптом | Причина и что делать |
| --- | --- |
| Ответ 502 на `/api/*` | Идёт пересоздание `api`: `caddy` находит его по DNS с обновлением раз в 10 секунд и на это время отвечает 502. Подождите и смотрите `docker compose … ps` |
| Keycloak долго стартует, `api` ждёт | Нормально, до минуты: дождитесь состояния `healthy` в `docker compose … ps` |
| 500 в API, `No space left on device` | Закончилось место на диске. Старые стенды держали под файлы весь объём заранее: пересоздание контейнера место освобождает не сразу. Для демонстрационного стенда проще пересоздать том (`docker compose … down`, `docker volume rm <проект>_seaweed_data`, `up -d`, затем `bash scripts/seed_demo.sh`: загруженные файлы пропадут). Для боевого нужен перенос данных |
| Интерфейс без шрифта Rostelecom Basis | Файлов шрифтов нет: положите `*.woff` в `compose/fonts/` (глава «TLS и домен»); работа не нарушена, меняется только гарнитура |
| Keycloak не стартует на «голом» виртуальном процессоре | Нужны инструкции x86-64-v2: тип процессора `host` или `x86-64-v2` (глава «Обзор и требования») |
| Ошибка `CRM-1105` на любом действии | Пользователь не принял согласие на обработку персональных данных: он принимает его в окне при входе |

## Высокая доступность

Симптомы схемы с тремя узлами (Patroni, etcd, файловый кластер) — в главе «Высокая доступность на трёх узлах», раздел «Если не получилось».

## Как проверить

Каждое решение завершается проверкой: `bash scripts/smoke.sh http://localhost:8080` завершается строкой «всё в порядке», на экране «Интеграции» плашки состояния зелёные.

## Если не получилось

Соберите последние сто строк журналов `api`, `worker`, `caddy` и `keycloak`, код обращения из окна ошибки и версию образов (`docker compose … images`) и передайте их разработчикам.
