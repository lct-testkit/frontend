# Масштабирование

Глава объясняет, что можно масштабировать на одном сервере Docker Compose, чего масштабировать нельзя и куда идти, если одного узла мало.

## Что понадобится

- Стенд, установленный по главе «Установка: онлайн и офлайн».
- Понимание нагрузки: что именно упирается, API или что-то другое (глава «Мониторинг и логи» даёт задержки, очередь и ошибки).

## Шаги: что масштабируется

Сервис `api` масштабируется репликами. У него нет фиксированного имени контейнера и портов на хосте: `caddy` находит реплики через DNS, обновляя список раз в 10 секунд, и распределяет запросы по принципу «наименее загруженная реплика».

```bash
docker compose -p rtk-demo -f compose/docker-compose.yml --env-file /srv/rtk-demo/.env \
  --env-file /srv/rtk-demo/.env.images up -d --scale api=3
```

Один процесс на контейнер: переменную `UVICORN_WORKERS` не меняйте (оставьте `1`). Счётчики метрик живут в памяти процесса, и при нескольких процессах сбор метрик видел бы лишь часть трафика. Prometheus (профиль `monitoring`) собирает метрики с каждой реплики `api` и `worker` отдельно.

Важная оговорка по поведению Docker Compose: число реплик задаётся ключом `--scale` в конкретной команде. Команда `up -d` без него (в том числе автоматическая выкладка `scripts/deploy.sh`) возвращает число реплик к значению из файла, то есть к одной. Эта оговорка взята из поведения Compose, в репозитории поставки не проверялась: после каждой выкладки проверяйте число реплик (`docker compose … ps api`) и при необходимости повторяйте команду со `--scale`.

Для сервиса `worker` в репозитории такая команда не описана. Prometheus собирает метрики с каждой реплики воркера отдельно, то есть схема несколько воркеров допускает, но на стенде это не проверялось: пробуйте на копии.

## Что не масштабируется

В схеме Compose по одному контейнеру на каждый из сервисов `postgres`, `redis`, `keycloak`, `seaweedfs`. Если нужна устойчивость базы и хранилища к потере узла, смотрите главу [«Высокая доступность на трёх узлах»](?s=admin-ha). Путь через Helm и Kubernetes экспериментальный: чарт проверяется статически, установка в кластер автоматически не проверяется.

## Как проверить

```bash
docker compose -p rtk-demo -f compose/docker-compose.yml --env-file /srv/rtk-demo/.env \
  --env-file /srv/rtk-demo/.env.images ps api
```

В выводе должно быть три контейнера `api`, все в состоянии работы. Выполните несколько запросов (например, откройте несколько страниц) и убедитесь на дашборде «API — здоровье и производительность», что запросы распределяются между репликами.

## Если не получилось

- После выкладки осталась одна реплика — см. оговорку выше: повторите команду со `--scale api=3`.
- Метрики искажены — убедитесь, что `UVICORN_WORKERS=1`.
- Остальное — в главе [«Неполадки»](?s=admin-troubleshooting).
