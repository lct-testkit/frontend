# Обзор и требования

Эта глава объясняет, из чего состоит система, на каком сервере её можно запустить и как понять, что она здорова. Остальные главы руководства администратора опираются на неё.

## Что понадобится

- Сервер с Linux и systemd (в руководстве везде имеются в виду Ubuntu или Debian).
- Docker и плагин Docker Compose версии 2: команда `docker compose version` должна отвечать. Установка Docker в руководство не входит: скрипт подготовки сервера проверяет его наличие, но сам не ставит.
- Права администратора сервера (root или sudo) для первой подготовки машины.
- Для установки из интернета: доступ к реестру образов `ghcr.io` и токен чтения пакетов. Для закрытого контура без интернета: готовый офлайн-пакет релиза (глава «Установка: онлайн и офлайн»).

## Из чего состоит система

Все сервисы запускаются одной командой Docker Compose и называются так же в логах и в таблице процессов.

| Сервис | Что делает |
| --- | --- |
| `caddy` | Единственная точка входа: принимает запросы, обслуживает TLS, отдаёт клиент, направляет `/api` в API, `/auth` в Keycloak, `/grafana` в Grafana |
| `web` | Веб-клиент (то, что открывается в браузере) |
| `api` | Серверное приложение: бизнес-логика и API |
| `worker` | Фоновые задачи: очередь событий и периодические задачи по расписанию |
| `migrate` и `seed` | Разовые задачи при запуске: обновление схемы базы и стартовые данные (воронки). После завершения они остаются в состоянии «Exited (0)» |
| `postgres` | База данных. Две логические базы в одном сервере: `crm` и `keycloak` |
| `redis` | Сессии, кэш, блокировки, очередь фоновых задач |
| `keycloak` | Вход пользователей, роли, политика паролей |
| `seaweedfs` | Хранилище файлов (S3-совместимое): вложения, отчёты, подписанные документы |
| `ntp` | Доверенное время для штампа электронной подписи |
| `sms-gateway-mock` | Имитация СМС-шлюза: код подписи уходит сюда, настоящего оператора в поставке нет |

Необязательные наборы сервисов включаются отдельно: `integrations` (заглушки `mock-lms` и `mock-cms` для проверки интеграций), `registry` (внутренний реестр образов для закрытого контура), `demo-data` (загрузка моковых данных) и `monitoring` (Prometheus и Grafana, глава «Мониторинг и логи»).

## Порты

| Режим TLS | Какие порты нужны |
| --- | --- |
| `acme` и `internal` | 80 и 443 (TCP, а 443 ещё и UDP для HTTP/3) и 8333 (файлы). Эти порты фиксированы, такой стенд на машине один |
| `off` | 8080 (http), 8443 (https с самоподписанным сертификатом), 8333; PostgreSQL публикуется только на самой машине (`127.0.0.1:5433`) |

Docker публикует порты в обход файрвола ufw, поэтому всё, что не должно быть видно снаружи, привязано к `127.0.0.1`. Подробнее — в главе «TLS и домен».

## Ресурсы и ограничения

В репозитории поставки нет проверенных нормативов по процессору и памяти, поэтому цифр «минимум» здесь нет. Что известно из документации:

- скрипт подготовки сервера заводит файл подкачки 2 ГБ;
- образ Keycloak собран для процессоров с набором инструкций x86-64-v2: на «голом» виртуальном процессоре QEMU он не стартует (ошибка `CPU does not support x86-64-v2`), нужен тип процессора `host` или `x86-64-v2`;
- пустой стенд сейчас занимает на диске мало: место под файлы выделяется по мере роста данных, а не заранее (до исправления пустой стенд занимал 20–36 ГБ).

## Пути развёртывания

| Путь | Когда выбирать |
| --- | --- |
| Docker Compose из репозитория `deploy` | Один сервер с интернетом. Основной поддерживаемый путь |
| Офлайн-пакет | Закрытый контур: все образы лежат в архиве релиза |
| Helm для Kubernetes | Экспериментальный: чарт проверяется статически, установка в кластер автоматически не гоняется |

На одной машине могут жить независимые окружения `dev`, `demo` и `prod`: каталоги `/srv/rtk-dev`, `/srv/rtk-demo`, `/srv/rtk-prod` и проекты Compose `rtk-dev`, `rtk-demo`, `rtk-prod`. Офлайн-установщик создаёт один проект `rtk-crm`.

## Шаги

1. Выберите путь развёртывания (таблица выше) и окружение (`demo` или `prod`).
2. Подготовьте сервер: Docker, Compose, порты, файл подкачки. Порядок — в главе [«Установка: онлайн и офлайн»](?s=admin-install).
3. После установки вернитесь к этой главе за проверкой состояния.

## Как проверить

Система отвечает на два адреса состояния:

```bash
curl http://localhost:8080/health/live
curl http://localhost:8080/health/ready
```

Первый отвечает, что приложение живо. Второй проверяет зависимости: ожидается `"status":"ok"` и `"ok":true` у `postgres`, `redis`, `keycloak_jwks`, `seaweedfs` и `queue`. В режимах `acme` и `internal` вместо `localhost:8080` используйте адрес стенда.

В самом интерфейсе то же видно на экране «Интеграции» (меню «Настройка»): плашки сверху показывают состояние базы, Redis, Keycloak, файлового хранилища и очереди задач.

![Раздел «Интеграции» под администратором: сверху плашка «Состояние системы»](/help/admin-health.png)

Версию установленной сборки показывает список образов:

```bash
docker compose -p rtk-demo -f compose/docker-compose.yml --env-file /srv/rtk-demo/.env --env-file /srv/rtk-demo/.env.images images
```

Сверьте тег и дайджест с файлом `images.yaml` репозитория `deploy`.
