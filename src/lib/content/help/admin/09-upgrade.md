# Обновление и откат

Глава описывает, как обновляется система, как вернуть предыдущую версию образов и почему откат не всегда возвращает базу данных.

## Что понадобится

- Установленный стенд из репозитория `deploy` (скрипт `scripts/deploy.sh`) или офлайн-пакет (отдельный раздел ниже).
- Свежая резервная копия и проверенный `restore_test.sh` (глава «Резервные копии и восстановление»): откат образов не откатывает базу.

## Как приходят обновления

Новый образ проходит гейты до того, как попадёт на стенд: разработчики публикуют образ только после проверок, затем репозиторий `deploy` перед записью образа в `images.yaml` поднимает стек с ним и запускает дымовой тест. Только после этого в `images.yaml` пишется новая версия образа. Единый источник истины по образам — `images.yaml`: сервер читает его через `git pull` и сам генерирует `.env.images`.

## Шаги: два пути обновления

### Автоматически (demo и dev)

Раз в 5 минут таймер systemd запускает `scripts/deploy.sh` под пользователем `deploy`: подтягивает репозиторий, пересчитывает `.env.images` и, если ничего не изменилось, выходит. Если образы новые:

1. снимается резервная копия (хранятся семь последних);
2. скачиваются образы, стек перезапускается командой `up -d --wait`;
3. запускается дымовой тест;
4. при любой ошибке образы возвращаются на предыдущие, а проваленные ссылки сохраняются в `.env.images.failed`.

```bash
sudo bash scripts/install_autodeploy.sh demo
systemctl status rtk-demo-autodeploy.timer
sudo systemctl start rtk-demo-autodeploy.service
journalctl -u rtk-demo-autodeploy.service -f
```

Первая команда включает таймер, вторая показывает расписание, третья прогоняет выкладку прямо сейчас, четвёртая следит за журналом. Окружение `prod` автообновлением не обслуживается намеренно: скрипт установки таймера для него откажется работать.

### Вручную (prod, и любое окружение при необходимости)

```bash
RTK_ENV=prod scripts/deploy.sh
```

Скрипт делает то же, что и таймер: копия «до», скачивание образов, `up -d --wait`, дымовой тест, возврат на прежние образы при сбое. Перед боевой выкладкой убедитесь, что последняя копия проверена `restore_test.sh`. Путь копии скрипт печатает.

### Офлайн-стенд

В поставке нет отдельной команды обновления для офлайн-установки. Повторный запуск установщика берёт окружение, адрес и режим TLS из существующего `compose/.env` и не трогает секреты и пароли базы. Исходя из этого, обновление выглядит так (по коду `install.sh`, на машине не проверялось, обязательно сначала сделайте копию):

1. Проверьте и распакуйте новый пакет релиза (глава «Установка: онлайн и офлайн»).
2. Скопируйте `compose/.env` из старого каталога в `compose/` нового.
3. Запустите `bash install.sh` из нового каталога: он загрузит новые образы и перезапустит стек с прежними данными.

Если на машинах контура работает внутренний реестр, образы доставляются через него (`bash install.sh --registry`, затем `python3 scripts/render_env_images.py --mode registry --registry registry.local:5000 > /srv/rtk-demo/.env.images` на каждой машине).

## Откат

```bash
RTK_ENV=demo scripts/deploy.sh rollback
```

Команда возвращает образы предыдущего успешного выкладывания (файл `.env.images.prev`), перезапускает стек и проверяет его дымовым тестом.

**Важно: откат не возвращает базу данных.** Миграции схемы идут только вперёд, откат образов схему не откатывает. Если новая версия успела применить необратимые миграции, восстанавливайте базу из копии, снятой перед выкладкой (путь печатает `deploy.sh`, копии лежат в `/srv/rtk-<окружение>/backups/`): сначала проверьте её `restore_test.sh`, затем восстановите в рабочий стенд (глава «Резервные копии и восстановление»).

Откат к произвольной версии образов: верните нужный коммит файла `images.yaml` и выкатите без `git pull`, затем обязательно верните файл из `main`, иначе следующий автодеплой перезапишет откат:

```bash
git -C <каталог-deploy> checkout <коммит> -- images.yaml && RTK_ENV=demo scripts/deploy.sh --no-pull
git -C <каталог-deploy> checkout main -- images.yaml
```

## Что сломалось и что делать

| Симптом | Что делать |
| --- | --- |
| `unauthorized` при скачивании образов | Токен чтения образов на сервере истёк или вход не выполнялся: повторите `docker login ghcr.io` под пользователем `deploy` (файл `docs/ghcr-setup.md`) |
| Таймер есть, образы не обновляются | Смотрите `journalctl -u rtk-demo-autodeploy.service`: возможен конфликт `git pull` (не правьте файлы в каталоге репозитория руками) или проверка нового образа на стороне разработки не прошла |
| После отката образы старые, а схема базы новее | Восстановление из копии «до выкладки» (см. выше) |
| Нужно понять, что реально задеплоено | `docker compose … images` и сверка тега и дайджеста с `images.yaml` |

## Как проверить

После выкладки или отката: `bash scripts/smoke.sh http://localhost:8080` завершается строкой «всё в порядке», в журнале деплоя последняя строка «готово» (или «откат выполнен»), на экране «Интеграции» плашка «Состояние системы» не показывает «Сервер работает частично» или «Сервер недоступен».

![Плашка «Состояние системы» в разделе «Интеграции» после обновления](/help/admin-health.png)

## Если не получилось

Выкладка провалена и после отката система тоже нездорова — нужно ручное вмешательство: смотрите журналы сервисов (глава «Мониторинг и логи») и главу [«Неполадки»](?s=admin-troubleshooting).
