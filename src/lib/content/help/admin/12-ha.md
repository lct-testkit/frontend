# Высокая доступность на трёх узлах

Схема, при которой падение любого одного из трёх серверов не останавливает сервис надолго: база переключается на реплику сама, адрес переезжает на нового лидера, приложение стартует на нём без вмешательства человека, а файлы лежат в двух копиях на разных площадках. Это не стандартная установка: её собирают вручную поверх обычного стека. Полный набор скриптов и конфигов — в файле `docs/ha-patroni.md` репозитория `deploy`; здесь схема, порядок работ и эксплуатация.

## Что понадобится

- Три сервера на разных площадках, связанные между собой частной сетью (в проверенной схеме — WireGuard, адреса `10.10.0.1`, `10.10.0.2`, `10.10.0.3`). Etcd, Patroni, репликация и файловый кластер ходят только по ней.
- На каждом узле Docker и плагин Compose, а также образы стека, загруженные заранее (стек должен подниматься без сети).
- Узел, который может стать лидером, должен поддерживать инструкции x86-64-v2 (`popcnt`, `sse4_2`): образ Keycloak без них падает с ошибкой `CPU does not support x86-64-v2`. Такой узел оставляют репликой с признаком `nofailover: true`.
- Управляемая DNS-зона, где запись типа A домена стенда можно менять по API (в проверенной схеме Cloudflare; скрипты берут идентификаторы зоны и записи из файла настроек).
- Включённый файрвол `ufw` на всех узлах: без него REST API Patroni и PostgreSQL окажутся открыты в интернет.

## Схема

| Узел | Площадка в проверенной схеме | Роль |
| --- | --- | --- |
| n1 | Москва, `10.10.0.1` | Основной лидер |
| n2 | Санкт-Петербург, `10.10.0.2` | Реплика базы, копия файлов, голос в кворуме; `nofailover: true` |
| n3 | Казань, `10.10.0.3` | Реплика базы, цель переключения |

- **База.** PostgreSQL 16 под управлением Patroni; хранилище состояния — etcd v3 на всех трёх узлах (кворум 2 из 3); репликация асинхронная потоковая.
- **Приложение.** Стек Compose (`docker-compose.yml` плюс `docker-compose.ha.yml`) запущен **только на лидере**; на репликах лежат образы и настройки, а стек остановлен. Контейнер `postgres` из обычного стека в этой схеме не нужен (заменён на `sleep infinity`): приложение ходит в PostgreSQL узла по имени `patroni-db`.
- **Файлы.** Кластер SeaweedFS на каждом узле (`/opt/seaweed`): три датацентра `dc1`, `dc2`, `dc3`, репликация `100` — две копии в разных датацентрах. Сервис `seaweedfs` основного стека на лидере — это filer и S3-шлюз: данные идут в кластер, метаданные filer лежат в PostgreSQL (база `seaweedfs`).
- **DNS.** При смене лидера запись A обновляет скрипт.
- **TLS.** Caddy в режиме `acme`; том `rtk-crm_caddy_data` лидер раз в 2 минуты раздаёт остальным узлам, чтобы после переключения не выпускать сертификат заново (у Let's Encrypt есть лимит на повторные выпуски).

## Как проходит переключение

1. Лидер перестаёт обновлять ключ в etcd. Через 30–40 секунд реплика берёт ключ и становится лидером. Изолированный бывший лидер сам понижает себя.
2. Patroni вызывает скрипт `/etc/patroni/cf_update_dns.sh` на событиях `on_start`, `on_restart` и `on_role_change`. Тот запускает `rtk-ha-stack.sh` отдельным системным юнитом через `sudo`.
3. `rtk-ha-stack.sh` берёт настоящую роль из REST Patroni и приводит узел к ней: лидер обновляет запись DNS и поднимает стек (`docker compose up -d`), остальные останавливают стек (`docker compose stop`). Скрипт идемпотентен, журнал — `/var/log/patroni-cf.log`.
4. Клиенты видят новый адрес после истечения кэша DNS.

Замеры 18.10.2026: плановое переключение — новый лидер за около 5 секунд, приложение готово ещё через около 25; аварийная изоляция лидера — новый лидер за 38 секунд, приложение готово через 62. Клиентам понадобилось 1–3 минуты из-за кэша DNS.

## Что проверено, а что нет

Проверено на трёх серверах стенда `lct.velikoss.ru`: плановое переключение туда и обратно (сайт, Keycloak и ранее записанный файл доступны после каждого); изоляция лидера от частной сети на 150 секунд (новый лидер, обновление DNS, остановка стека на старом, возврат репликой); остановка файлового кластера на лидере при работающем приложении (чтение и запись файлов не прерывались).

Не проверялось: жёсткое выключение лидера питанием, одновременная потеря двух узлов, чтение файлов с нового лидера в момент изоляции прежнего.

## Шаги

Порядок развёртывания (подробности и все файлы — в `docs/ha-patroni.md`, приложение A):

1. Настройте частную сеть между узлами.
2. Поставьте etcd v3 на каждый узел и Patroni (юнит `patroni.service`) с `etcd3.hosts` на три узла; в `patroni.yml` включите обработчики событий на `/etc/patroni/cf_update_dns.sh` и признак `nofailover` (true для узла, который не должен становиться лидером).
3. Создайте базы с локалью `C.UTF-8` (не `ru_RU.utf8`: иначе узлы с другим дистрибутивом либо не примут подключения, либо получат несогласованные индексы) и восстановите данные: базы `crm`, `keycloak`, `seaweedfs`, роли `crm`, `crm_app`, `seaweed`.
4. Поднимите файловый кластер SeaweedFS на каждом узле (`/opt/seaweed`, переменные `NODE_IP` и `DC`, каталоги `/srv/seaweed/{master,volume}`). Репликацию держите `100`: при `200` запись встаёт, как только падает один из трёх узлов.
5. Положите `docker-compose.ha.yml` и `runtime/seaweedfs/filer.toml` в `/opt/rtk-crm/compose` на всех узлах; задайте пароль роли `seaweed` и впишите его в `filer.toml` (права `600`). Файлы `.env`, `.env.images`, `Caddyfile`, `docker-compose.yml` и каталог `runtime/` должны быть одинаковы на всех узлах, пути в `.env` (`SEAWEED_S3_CONFIG`) абсолютные и одинаковые.
6. Установите скрипты `/usr/local/sbin/rtk-ha-stack.sh`, `/usr/local/sbin/rtk-ha-trigger.sh` (права 755, владелец root), `/etc/patroni/cf_update_dns.sh`, `/etc/sudoers.d/rtk-ha` (права 440) и файл настроек DNS `/etc/patroni/cf.env` (токен, идентификатор зоны и записи, домен, публичный IP узла).
7. Настройте синхронизацию сертификата Caddy: общий ключ на всех узлах и таймер `rtk-caddy-sync.timer`.
8. Первый запуск на лидере: `/usr/local/sbin/rtk-ha-trigger.sh manual master` обновит DNS и поднимет стек.

## Эксплуатация

```bash
patronictl -c /etc/patroni/patroni.yml list
patronictl -c /etc/patroni/patroni.yml switchover crm --leader n1 --candidate n3 --force
tail -f /var/log/patroni-cf.log
systemctl list-timers rtk-caddy-sync.timer
curl -s http://10.10.0.1:9333/dir/status | jq '.Topology.DataCenters[].Id'
```

По порядку: состояние кластера; плановое переключение; что делал обработчик событий; синхронизация сертификата; топология файлового кластера (должны быть три датацентра).

## Ограничения

- Репликация асинхронная: при внезапной потере лидера теоретически теряются последние миллисекунды коммитов. Вариант — `synchronous_mode: true`, но тогда на узле с `nofailover` нужен ещё `nosync: true`.
- Сессии (Redis, Keycloak) живут на лидере и при переключении сбрасываются: пользователям нужно войти заново.
- Доступность для клиентов ограничена кэшем DNS (в тестах 1–3 минуты). Если обработчик не смог обновить DNS за пять попыток, поправьте запись вручную или повторите `rtk-ha-trigger.sh manual master` на лидере.
- Резервных копий по расписанию в этой схеме нет: настройте `pg_dump` на лидере и копирование данных файлового хранилища.

## Как проверить

После развёртывания `patronictl … list` показывает один лидер и две реплики без задержки репликации, топология SeaweedFS — три датацентра, `smoke.sh` на лидере зелёный. Плановое переключение (`switchover`) и возврат должны занимать около полуминуты до готовности приложения.

## Если не получилось

Типичные ловушки, на которые уже наступили:

- обработчик, запущенный из процесса Patroni, наследует его группы: если `postgres` добавили в `docker` после старта Patroni, команды Docker недоступны (`permission denied`). Поэтому обработчик идёт через `sudo` и отдельный системный юнит;
- команда `docker compose stop` с устаревшим именем сервиса в списке не останавливает **ничего**, поэтому в скрипте `stop` вызывается без списка;
- filer ходит к мастеру на хост по адресу частной сети; правила ufw для сетей Docker (`172.16.0.0/12`) должны пускать порты 9333 и 19333, иначе filer бесконечно «ждёт мастера»;
- filer не должен ходить в PostgreSQL по публичному имени домена: используйте `patroni-db`;
- без синхронизации сертификата Caddy он перевыпускается на каждом новом лидере.
