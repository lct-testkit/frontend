# Резервные копии и восстановление

Глава описывает, что входит в резервную копию, как проверить, что копию можно восстановить, и как вернуть данные в рабочий стенд.

## Что понадобится

- Скрипты `scripts/backup.sh` и `scripts/restore_test.sh` из репозитория `deploy`. Важно: в офлайн-пакет релиза они **не входят** (в пакете `gen_env.sh`, `lib_host.sh`, `set_host.sh`, `registry_load.sh`, `smoke.sh`, `seed_demo.sh` и `install.sh`), поэтому перенесите каталог `scripts/` из репозитория на машину.
- Свободное место: копия содержит дампы баз и архив всего тома файлов.
- Место для хранения копий **вне сервера**, включая копию файла `.env` (см. ниже).

В командах ниже окружение `demo` из `/srv/rtk-demo`. Для офлайн-установки проект называется `rtk-crm`, а `.env` и `.env.images` лежат в каталоге `compose/` рядом с `install.sh`.

## Что входит в копию и что нет

Каждый запуск `backup.sh` создаёт каталог `<проект>-<дата и время UTC>`, в нём:

| Файл | Что это |
| --- | --- |
| `crm.dump`, `keycloak.dump` | Базы приложения и Keycloak (пользователи и настройки входа) |
| `globals.sql` | Роли кластера PostgreSQL, включая ограниченную роль приложения. Содержит хэши паролей, права `600` |
| `seaweed_data.tgz` | Архив тома хранилища файлов |
| `counts.tsv` | Число строк в таблицах на момент копии — эталон для проверки |
| `SHA256SUMS` | Контрольные суммы всех файлов |

**Не входят:** файл `.env`, а с ним ключи `AUDIT_HMAC_KEY` и `SETTINGS_ENCRYPTION_KEY`; сгенерированные `runtime/keycloak/realm-crm.json` и `runtime/seaweedfs/s3.json`; сертификаты Caddy (том `caddy_data`); Redis (сессии, их потеря означает только повторный вход). Без `.env` и ключей восстановленную базу не расшифровать и не подписать заново. Храните копию `.env` и каталога `runtime/` вне сервера вместе с архивами. Эти файлы содержат секреты: не отправляйте их в чат и почту.

## Шаги: сделать копию

```bash
bash scripts/backup.sh --env-file /srv/rtk-demo/.env --images-env /srv/rtk-demo/.env.images \
                       --project rtk-demo --out /srv/rtk-demo/backups
```

Последняя строка вывода — путь к созданной копии. Копию также снимает автоматически `scripts/deploy.sh` перед каждой выкладкой; хранятся семь последних (значение `KEEP_BACKUPS`).

**Расписания в поставке нет.** Для суточной копии настройте запуск этой команды в вашем планировщике (cron или таймер systemd). При суточной копии потери при аварии могут достигать суток; целевой показатель в спецификации (15 минут) потребовал бы архивирования журнала транзакций, а в репозитории оно не реализовано.

## Шаги: проверить копию

Непроверенная копия ничего не гарантирует. Проверка поднимает отдельный чистый стенд (проект `rtk-restore-test`, порты 18080, 18443, 18333, 15433), восстанавливает в него базы, сверяет число строк по `counts.tsv`, поднимает весь стек и запускает дымовой тест. Боевой стенд она не трогает.

```bash
bash scripts/restore_test.sh --backup /srv/rtk-demo/backups/<каталог> \
     --env-file /srv/rtk-demo/.env --images-env /srv/rtk-demo/.env.images
```

Проверка не восстанавливает том файлов: архив `seaweed_data.tgz` сверяется только по контрольной сумме. Чтобы убедиться, что он читается, выполните `tar tzf seaweed_data.tgz`.

## Шаги: восстановить в рабочий стенд

Готовой команды «восстановить в боевой стенд» в поставке нет: скрипт проверки восстанавливает только в изолированный стенд. Ниже процедура, собранная из тех же шагов, что делает `restore_test.sh`. **Она не отрабатывалась на боевом стенде:** сначала проведите её целиком на копии, не на единственном рабочем экземпляре.

1. Проверьте копию и остановите сервисы, которые держат базы:

   ```bash
   DC="docker compose -p rtk-demo -f compose/docker-compose.yml --env-file /srv/rtk-demo/.env --env-file /srv/rtk-demo/.env.images"
   B=/srv/rtk-demo/backups/<каталог>
   (cd $B && sha256sum -c SHA256SUMS)
   $DC stop caddy api worker keycloak seaweedfs
   ```

2. Пересоздайте базы и восстановите в них данные. Имя пользователя `crm` — значение `POSTGRES_USER` по умолчанию; ошибки «already exists» при применении ролей — норма:

   ```bash
   $DC exec -T postgres psql -U crm -d postgres -c 'DROP DATABASE crm' -c 'DROP DATABASE keycloak' -c 'CREATE DATABASE crm' -c 'CREATE DATABASE keycloak'
   $DC exec -T postgres psql -U crm -d postgres < $B/globals.sql
   $DC exec -T postgres pg_restore -U crm -d crm --no-owner < $B/crm.dump
   $DC exec -T postgres pg_restore -U crm -d keycloak --no-owner < $B/keycloak.dump
   ```

3. Файлы. Том `rtk-demo_seaweed_data` перед распаковкой должен быть пустым. Удалите старый том (`docker volume rm rtk-demo_seaweed_data`, сервис к этому моменту остановлен) и распакуйте архив в новый тем же образом, каким он создавался: команда обратная той, что в `backup.sh` (`tar xzf` вместо `czf`):

   ```bash
   docker run --rm --entrypoint tar -v rtk-demo_seaweed_data:/data -v $B:/backup <образ-seaweedfs-из-.env.images> xzf /backup/seaweed_data.tgz -C /data
   ```

   Имя образа смотрите в `.env.images` в переменной `SEAWEEDFS_IMAGE`.

4. Поднимите стек и проверьте:

   ```bash
   $DC up -d --wait
   bash scripts/smoke.sh http://localhost:8080
   ```

5. Войдите в систему, откройте сделку, скачайте приложенный к ней файл.

Если в `.env` изменились `AUDIT_HMAC_KEY` или `SETTINGS_ENCRYPTION_KEY`, верните прежние значения из сохранённой копии `.env`.

## Как проверить

После `restore_test.sh` итоговая строка: «ВОССТАНОВЛЕНИЕ ПРОВЕРЕНО» с путём копии. После восстановления в рабочий стенд: дымовой тест зелёный, под администратором открывается «Журнал аудита», кнопка «Проверить целостность» даёт зелёный результат, файл сделки скачивается.

## Если не получилось

- `restore_test.sh` пишет, что данные после восстановления не совпадают с копией — копия повреждена или снята не полностью; повторите копию.
- Файлы не скачиваются после восстановления — том файлов восстановлен не тем архивом или не в тот проект.
- Остальное — в главе [«Неполадки»](?s=admin-troubleshooting).
